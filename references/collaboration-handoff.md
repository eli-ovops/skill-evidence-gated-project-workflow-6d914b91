# 协作、交接与独立验收

## 角色使用通用名

- **治理/PMO**：确认范围、授权、Owner、风险和验收结论；不下场替代执行。
- **Owner**：对实际修改、验证、证据和回滚负责。
- **协作者**：只处理边界清晰的局部任务，不扩大范围。
- **独立审查者**：基于任务、版本和证据检查，不以作者预期结论为目标。

不得把 Codex、Claude、Reasonix 或其他产品名称永久绑定为组织角色；模型变化不应改变责任链。

## 单一权威链

优先级始终服从平台、当前用户要求、全局规则和项目规则。协作文档只记录项目事实与交接，不建立第二套宪法，也不自动覆盖最新任务单。

只在以下情况留档：

- 产生可复用决定或冻结边界；
- Owner/线程发生交接；
- 高风险验收、失败或回滚；
- 后续任务无法仅靠代码/提交理解。

普通探针和机械动作不要求一动作一文档。

## 派单最小字段

```text
目标：
任务边界与禁止事项：
输入版本/路径：
授权与环境：
唯一Owner：
验收标准与证据：
必需验收层级（每层 Owner / 方法 / 触发条件）：
失败停止条件：
回报对象：
```

## Owner回报

```text
承接依据：
实际修改/动作：
未修改范围：
验证命令与结果：
证据位置：
偏差、风险和残余未知：
回滚/退出路径：
建议状态：待验收
```

Owner 自述只能进入待验收，不能直接成为最终通过。

## 分层验收与补验

派单前把本任务的必需验收层级写清，例如代码、build、本地、
浏览器、生产或用户验收。某一层通过只关闭该层；任一必需层未完成
时，状态不得无范围写成“完成”或“闭环”。

非必需检查只记录其限制和不覆盖的范围，不自动扩大任务。补验条目
必须写明 Owner、具体方法和触发条件；没有这三项只能标为待定义，不能
用“稍后补验”代替当前证据。

## 独立审查

审查者至少完成：

1. 核对任务对象、版本、范围和授权；
2. 从结论反向追到实际证据；
3. 从关键输入正向检查遗漏和过度解读；
4. 检查正常、边界、失败、反方和恢复场景；
5. 检查是否用工具输出、截图、HTTP 200 或作者自述替代目标验收；
6. 给出通过、条件通过、未通过或未验证。

审查发现格式：

```text
ID / 严重度 / 位置 / 违反规则 / 事实证据 / 影响 / 修正 / Owner / 复验证据 / 状态
```

作者可解释和修复，但不能代替独立结论。只改措辞不能关闭事实或数据缺陷。

## 冲突与变更

- 新事实与冻结边界冲突时，先标记冲突，不静默覆盖。
- 重要决定变更需说明背景、原因、影响、迁移和回滚。
- 两个执行者不得同时修改同一范围；并行任务必须有独立输入输出。
- 协作者失败、超时或工具不可用时记“检查未完成”，不得投票或猜测为通过。

## 交接包

只交接最小充分信息：目标、完成/未完、风险、关键路径、Owner、验证证据、下一步、避坑、继承/废弃规则。避免复制完整历史、长工具输出和重复权威正文。
