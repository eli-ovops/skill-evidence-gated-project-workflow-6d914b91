# 后端架构设计与验收

## 先判断是否需要

先标记每项 `适用 / 不适用 / 待确认`：数据库、认证、权限、异步任务、文件/媒体、外部服务、审计、幂等、迁移、备份、监控和生产部署。没有业务需求时不得为了模板创建占位架构。

## 设计输入

- 用户场景、核心业务循环与明确不做范围；
- 数据主体、关键状态和一致性要求；
- 读写边界、权限边界和外部依赖；
- 预计规模、故障容忍、隐私/合规要求；
- 当前语言、框架、仓库、运行和部署事实；
- MVP、演示、内部工具或生产系统的真实阶段。

## 最小架构决定

重要选择使用精简决策记录：

```text
背景与约束：
要解决的决定：
候选方案：
选择及理由：
未选方案及理由：
预期后果与债务：
失败方式：
验证与回滚/退出路径：
```

选型优先考虑项目适配、团队熟悉度、官方文档、维护状态和可验证性，不以“更高级/安全/高性能”的标签代替证据。

## 框架与自定义边界

优先使用框架成熟机制处理路由、参数校验、HTTP状态、错误、中间件、日志和依赖管理。每个自定义封装必须回答：

1. 解决哪个当前问题；
2. 框架机制为何不足；
3. 去掉它的影响；
4. 当前是否实际使用；
5. 谁维护，如何测试和退出。

新增依赖、目录、错误协议或框架变更必须记录理由和兼容影响。秘密、端口和数据库地址不得硬编码进业务代码。

## 最小纵向切片

不要先建空洞“大骨架”。选择一个最小但真实的业务动作，走通适用环节：

`请求入口 → 校验 → 权限（如适用）→ 业务规则 → 数据访问（如适用）→ 响应/错误 → 日志/观测`

基础能力按适用性选择：启动入口、配置样板、健康检查、日志、测试、数据库连接、认证/权限、README。Demo 不得伪装成生产能力。

## 分级验收

### P0：架构起点

- 业务边界、阶段和不做范围可定位；
- 目录/模块责任清楚，无同类逻辑多套写法；
- 启动命令和实际结果；
- 配置来源与秘密边界；
- 最小切片真实运行证据；
- 成功、参数错误、资源不存在和系统异常；
- 认证/权限、数据库、日志仅在适用时提供实际证据。

### P1：进入持续开发

- 列表/详情/创建/更新/删除仅按真实接口范围验收；
- 数据迁移、幂等、审计、重试、异步任务按风险验收；
- 测试覆盖关键规则与失败路径；
- 依赖和自定义封装有维护与退出策略。

### 生产前专项

安全、隐私、容量、备份恢复、迁移、监控告警、部署回滚、真实环境和用户流程必须按现行专项规则另行验收。本参考不提供生产授权。

## 证据格式

每项写明：规则来源、代码/文件位置、验证命令、实际结果、证据位置、状态和影响。状态只用：

- 通过：规则、实现、执行和证据一致；
- 条件通过：非硬阻断，含Owner、期限和补偿控制；
- 未通过：执行结果违反规则；
- 未验证：未执行或证据不足。

关键安全、数据完整性、启动、边界或回滚问题为未通过/未验证时，不得宣布可生产或稳定完成。

## 反形式主义

- 文件或目录数量不是质量指标。
- “统一了、优化了、符合最佳实践”不是证据。
- 不要求所有项目拥有数据库、权限中间件或统一响应包装。
- 不用完整业务功能替代架构演练，也不让架构清单阻止低风险的最小验证切片。
